# Power Mode Switcher: Project Plan

A tiny Windows 11 desktop widget with a three-position slider that switches the Windows Power Mode between **Best power efficiency**, **Balanced**, and **Best performance**. It sits on the desktop (below all app windows), starts with Windows, and stays in sync if the mode is changed anywhere else.

Built with Claude Code. Developed and tested on a Windows 11 laptop with Modern Standby.

---

## 1. Goals and non-goals

### Goals
- Small floating widget with a 3-stop slider: Battery / Balanced / Performance.
- Widget lives at desktop level: below normal application windows, above the wallpaper and desktop icons.
- Starts automatically when the user signs in to Windows.
- Slider updates itself when Power Mode changes outside the app (Windows Settings, the battery flyout, plugging in or unplugging, Battery Saver, and so on).
- Very low resource use while idle.
- Tray icon with a small menu for settings and exit.

### Non-goals (for now)
- Global hotkey.
- Code signing. (Expect a one-time SmartScreen "Run anyway" prompt.)
- Switching classic power plans with `powercfg`. See section 3.
- Installer. A single .exe in a folder is enough.

## 3. How Windows Power Mode actually works (read this first)

On Modern Standby laptops, Windows 11 usually exposes only the **Balanced** power plan. The Settings page "Power mode" dropdown is a separate layer called a **power overlay scheme**. This app controls the overlay, not the plan.

**Do not use `powercfg /setactive` for switching.** It changes the plan, not the Power Mode, and has no visible effect on this machine.

### Power mode GUIDs

**Source: [`docs/power-mode-guids.md`](docs/power-mode-guids.md), section 1.** That file is the reference for every power mode GUID, its labels and its order; keep this table and the code in step with it. Windows only has these four; PC makers do not add their own (they map their mode names onto these, see section 2 of that file).

| Order | GUID | Label | Notes |
|---|---|---|---|
| 1 | `961cc777-2547-4f9d-8174-7d86181b8a7a` | Best power efficiency (`GUID_POWER_MODE_BEST_EFFICIENCY`) | Standard set only |
| 2 | `00000000-0000-0000-0000-000000000000` | Balanced (`GUID_POWER_MODE_NONE`) | In both sets, but at a **different stop** in each (middle in Standard, bottom in Classic) |
| 3 | `3af9b8d9-7c97-431d-ad78-34a8bfea439f` | Better performance (not in the documented list) | Classic set only. Shown in Windows 11 Settings on Classic machines |
| 4 | `ded574b5-45a0-4f42-8737-46345c09c238` | Best performance (`GUID_POWER_MODE_BEST_PERFORMANCE`) | Top stop in both sets |

`3af9b8d9` is a performance-leaning mode. Before 2026-11-24 the app wrongly treated it as "better battery" and put the knob on the bottom stop. If any other GUID is read, show the slider in a neutral "unknown" state rather than guessing.

### API calls (all in `powrprof.dll`)

| Purpose | Function | Notes |
|---|---|---|
| Read and set mode (Windows 11) | `PowerGetUserConfiguredACPowerMode` / `PowerGetUserConfiguredDCPowerMode`, `PowerSetUserConfiguredACPowerMode` / `PowerSetUserConfiguredDCPowerMode` | **Documented** (Windows 11). Separate values for plugged in (AC) and on battery (DC); the app uses the one for the current power source. Only the three documented GUIDs are supported values. Used first. |
| Set mode (fallback) | `PowerSetActiveOverlayScheme(const GUID*)` | Undocumented but widely used and stable. Returns 0 on success. Takes a **pointer** to the GUID: declared `in Guid`. Passing it by value works by accident on x64 and fails on ARM64. |
| Read mode (fallback) | `PowerGetActualOverlayScheme(out Guid)` | Undocumented. Fallback for older Windows, and the only way to see `3af9b8d9`. |
| Watch for changes | `PowerRegisterForEffectivePowerModeNotifications` | **Documented** (Windows 10 1809+). Fires when the effective mode changes. Use it as a trigger, then re-read. Unregister on exit. |

The documented API and the undocumented overlay functions were checked against each other on the development laptop (Windows 11 build 26200): same values for both power sources, setting the current value is accepted and changes nothing, and an invalid GUID is rejected with error 87.

### Mode sets: not every PC offers the same three

Confirmed 2026-11-25 by reading the registry (`ActiveOverlayAcPowerScheme`) while picking each option in Settings on two Windows 11 laptops. Both show three options, but **not the same three**:

| Set | Bottom stop (ice cube) | Middle stop (sailboat) | Top stop (rocket) | Seen on |
|---|---|---|---|---|
| **Standard** | `961cc777` Best power efficiency | `00000000` Balanced | `ded574b5` Best performance | Development laptop (Dell, Windows 11) |
| **Classic** | `00000000` Recommended | `3af9b8d9` Better performance | `ded574b5` Best performance | Surface Laptop (Windows 11) |

Classic machines do not offer `961cc777` at all. Version 1.1.0 assumed Standard everywhere, so on the Surface: Recommended showed the sailboat, Better performance showed no knob, and the bottom stop set `961cc777`, which Windows accepted but Settings could not display. Phase 8 fixes this. Windows 10 is not a target and is untested.

Wrap all of these in one class (`PowerModeService`) so the undocumented parts sit in one place and can be swapped if Windows ever changes them.

### Things that also change the mode (the slider must follow them)
- **Plugged in vs on battery.** Windows stores a separate Power Mode for each. When the power source changes, the effective mode can jump. Listen for `SystemEvents.PowerModeChanged` (or `WM_POWERBROADCAST`) and re-read.
- **Battery Saver** turning on or off.
- **Energy Saver** (Windows 11 24H2+; it replaced Battery Saver and can be on while plugged in). Tested 2026-11-22: turning it on sends `GUID_ENERGY_SAVER_STATUS` = 1 and drops the *effective* overlay to best power efficiency, but the *actual* overlay (the user's chosen mode) does not change and the old Battery Saver flag (`SYSTEM_POWER_STATUS.SystemStatusFlag`) stays 0. So the slider stays on the chosen mode, and the widget and tray tooltip say "Energy Saver on". The app listens with `PowerSettingRegisterNotification(GUID_ENERGY_SAVER_STATUS)`.
- Changes from Windows Settings or the battery flyout.
- PC maker utilities may change the Windows power mode themselves (Dell Optimizer's sync setting, Lenovo auto mode, G-Helper on ASUS). The widget follows outside changes, so this works. HP and Acer modes run alongside Windows Power Mode without changing it. Details: `docs/power-mode-guids.md` section 2.
- Power Mode only applies on the Balanced power plan or one derived from it (plan GUIDs: `docs/power-mode-guids.md` section 3).

### Fallback
Add a simple poll every 5 seconds as a safety net in case a notification is missed. It costs almost nothing. Only update the UI if the value actually changed.

## 4. The widget window

### Look (matches the original design mockup)
- **Vertical** widget, about 230 x 340 pixels at 100% scaling.
- Panel: corner radius 20, background navy `#0F2F4C` at about 85% opacity, 1 px border in white at 14% opacity, 20 px padding.
- Left side: a vertical track 88 x 300, fully rounded (radius 44), white at 8% opacity, with a small 6 px dot at each of the three stops.
- The knob is an 80 x 80 round image that sits on the track and **changes picture by position**:

| Position | Mode | Knob image |
|---|---|---|
| Top | Best performance | `knob-performance-rocket.svg` (rocket with flames, red) |
| Middle | Balanced | `knob-balanced-sailboat.svg` (sailboat, teal) |
| Bottom | Best power efficiency | `knob-battery-ice.svg` (ice cube, blue) |

- Knob centers sit at 50, 150 and 250 px down the track. The knob has a soft drop shadow.
- When the mode changes, the knob slides to its new spot over about 200 ms with an ease-out curve (no bounce), and its image swaps.
- Right side: labels "Performance", "Balanced", "Battery", each vertically centered on its stop. The current one is white, 15 px, semibold; the others are white at about 62% opacity, 13 px, medium.
- Font: Inter if installed, otherwise Segoe UI.
- Clicking a stop, a label, or dragging the knob and releasing near a stop all change the mode.
- Optional small text line under the widget: "On battery" / "Plugged in".
- Crisp at any display scaling (per-monitor DPI aware, V2).

### Images
- The three SVGs above live in `src/PowerModeSwitcher/Assets/` and are the source images. WPF cannot show SVG directly, so they were hand-converted to WPF vector drawings in `Assets/KnobImages.xaml` (no package needed, sharp at any scaling). Keep both in sync.
- Tray icons: three .ico files made from the same drawings (16 to 48 px for the tray, plus 64 and 256 px for the .exe icon), so the tray icon also shows ice cube, sailboat or rocket. Regenerate them with `tools/make-icons.ps1`.

### Behavior
- Click or drag the slider to change mode. The change applies immediately.
- If setting the mode fails, snap the slider back to the real current value and show a brief tooltip with the error.
- Drag the widget by its background to reposition it. Save the position to settings and restore it at next launch.
- "Lock position" option in the tray menu to prevent accidental drags.
- If the saved position is off-screen (monitor unplugged), move the widget to the bottom-right of the primary screen.
- **Show mode names** (added 2026-11-22): menu switch, on by default. When off, the labels are hidden and the widget narrows to just the track (128 px wide at full size).
- **Half-size widget** (added 2026-11-22): menu switch, off by default. Scales the whole widget to 50%. When the size changes, the corner nearest the screen edge stays in place.

### Desktop-level z-order (the tricky part)
The widget should stay **below** normal windows and never pop in front of them.

Approach, in order:
1. Window style: no border, no taskbar button (`ShowInTaskbar = false`), add `WS_EX_TOOLWINDOW` so it does not appear in Alt+Tab, and `WS_EX_NOACTIVATE` so clicking it does not steal focus from other apps.
2. On startup, place it at the bottom of the z-order with `SetWindowPos(hwnd, HWND_BOTTOM, ..., SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`.
3. Hook `WM_WINDOWPOSCHANGING` and force `hwndInsertAfter = HWND_BOTTOM` every time, so nothing can bring it to the front (including clicking on it).

**Known issue to test:** pressing **Win+D** (Show Desktop) may hide the widget along with everything else. To make it survive Win+D, a stretch option is to parent the window into the desktop shell (the `Progman` / `WorkerW` window). This is more fragile and changed in recent Windows 11 builds, so do it only after the basic version works, behind a setting, and test carefully.

**Phase 3 result (2026-11-22):** Win+D hides the widget. Pressing Win+D again brings it back. Accepted for now; surviving Win+D stays in "Optional later".

## 6. Startup and settings

- **Start with Windows** on by default. Writes `PowerModeSwitcher` to `HKCU\...\Run` pointing at the current .exe path. If the .exe is moved, the next launch rewrites the path.
- **Single instance:** use a named mutex. A second launch just shows the existing widget and exits.
- `settings.json` fields: `WindowLeft`, `WindowTop`, `PositionLocked`, `WidgetVisible`, `ShowModeNames`, `HalfSize`, `StartWithWindows`.
- Should not require administrator rights. Verify in phase 1.

### Phase 6: Code quality fixes (from a code review)

A professional developer reviewed the repo and asked for two changes.

**6a. JSON source generation**
- `Services/SettingsService.cs` currently uses reflection-based `JsonSerializer` calls with a `JsonSerializerOptions` object. Replace them with System.Text.Json source generation: a `partial class AppJsonContext : JsonSerializerContext` with `[JsonSerializable(typeof(AppSettings))]` (and any other type saved to disk), and use `AppJsonContext.Default.AppSettings` in every serialize and deserialize call.
- Use `[JsonSourceGenerationOptions(WriteIndented = true)]` so `settings.json` stays human-readable.
- Existing `settings.json` files must still load, including ones missing newer fields. Test with the file already on the development laptop.

**6b. Native API declarations**
- Add the `Microsoft.Windows.CsWin32` package and a `NativeMethods.txt` listing every documented Win32 function, struct and constant the app uses today (for example `SetWindowPos`, `GetWindowLongPtr`/`SetWindowLongPtr`, `GetWindowRect`, `GetCursorPos`, `SetForegroundWindow`, `GetSystemPowerStatus`, `PowerSettingRegisterNotification`, `PowerRegisterForEffectivePowerModeNotifications` and their unregister functions, and the `WS_EX_*`, `SWP_*` and `HWND_*` values). Replace the hand-written `[DllImport]` declarations for those with the generated ones.
- The undocumented overlay functions (`PowerSetActiveOverlayScheme`, `PowerGetActualOverlayScheme`) are not in CsWin32's metadata. Keep them hand-written, but convert them to `[LibraryImport]` with source-generated marshalling. Put them in one small file with a comment explaining why they are hand-written.
- Check whether a documented Windows Runtime API can read the current effective power mode. Use it only if it works cleanly in a WPF .NET 10 app without a heavy dependency; otherwise keep the documented Win32 notification. Report the finding either way.
- Behavior must not change at all.

**Check:** run the full section 9 checklist on the development laptop. Everything works exactly as before. Write a short plain-language summary of what changed that can be forwarded to the reviewer.

**Phase 6 notes (2026-11-24):**
- JSON: `AppJsonContext` (source-generated, indented). `JsonSerializerIsReflectionEnabledByDefault=false` in the project, so any reflection-based call fails immediately. An older `settings.json` without `ShowModeNames`/`HalfSize` loads with defaults; a damaged file falls back to defaults.
- Win32: CsWin32 0.3.371 (build-time only) generates every documented declaration from `Native/NativeMethods.txt`, including `GUID_ENERGY_SAVER_STATUS`. `Native/PowerOverlayApi.cs` holds the two undocumented overlay functions as `[LibraryImport]`; they return `uint` (cast to `WIN32_ERROR`) because source-generated P/Invoke does not accept the generated enum. APIs newer than Windows 10 RTM (`PowerRegisterForEffectivePowerModeNotifications`, `GetDpiForWindow`) are behind `OperatingSystem.IsWindowsVersionAtLeast` checks, which the platform analyzer understands.
- WinRT: `Windows.System.Power.PowerManager` (built into Windows) reports battery, power supply and saver status but not the power mode. The Windows App SDK's `PowerManager.EffectivePowerMode` does, but it needs the Windows App SDK runtime (heavy for an unpackaged WPF app) and only reports the *effective* mode, not the user's chosen overlay the slider needs. Kept the documented Win32 notification.
- Framework-dependent .exe grew from 594 KB to 788 KB (generated code).
- **Check passed (2026-11-24):** the full section 9 checklist passed on the development laptop with the Phase 6 build.

**Phase 6 follow-up (2026-11-24, from `docs/power-mode-guids.md`):**
- The documented Windows 11 power mode API exists (section 4a of that file), which updates the WinRT finding above: Windows 11 has a documented Win32 API. It is now generated by CsWin32 and used first for reading and setting; the undocumented overlay functions are the fallback (older Windows, unknown power source, or `3af9b8d9`). Tested against the overlay functions on the development laptop before switching.
- `PowerSetActiveOverlayScheme` now takes the GUID by reference (`in Guid`), which fixes the ARM64 crash before Phase 9 (section 4b). Confirmed in the generated code: it passes a `Guid*`.
- `3af9b8d9` is now "Better performance" (section 1), not best power efficiency. With three stops it has no stop: the knob hides and the status line and tooltip name it. Phase 8 can give it a real stop.
- The three documented GUIDs now come from CsWin32's `GUID_POWER_MODE_*` constants.

### Phase 8: Mode sets and diagnostics

Replaces the earlier "learn mode" plan. Research and testing showed there are only four power mode GUIDs and two sets of three (section 3, "Mode sets"), so a learning wizard is not needed. The widget keeps exactly three stops and the same three images; only the GUIDs and labels behind each stop change with the set.

**8a. Copy diagnostics (build this first)**
- Right-click menu item **Copy diagnostics** copies plain text to the clipboard: Windows version and build, device manufacturer and model, power source, Energy Saver state, the current mode set and how it was chosen (detected, asked, or picked by the user), the plugged-in and on-battery modes from **both** the documented API and the registry values `ActiveOverlayAcPowerScheme` / `ActiveOverlayDcPowerScheme`, the actual and effective overlay, the effective power mode (`EFFECTIVE_POWER_MODE`), the active power plan GUID and name, and the names of the subkeys under `HKLM\SYSTEM\CurrentControlSet\Control\Power\User\PowerSchemes`.
- Reading those registry values needs no admin rights. Read only; never write the registry.

**8b. Two built-in mode sets**
- Define Standard and Classic exactly as in section 3. Each stop has a GUID, a label and a knob image (ice cube, sailboat, rocket from bottom to top).
- Labels everywhere (widget, menu, tray tooltip) come from the current set: Standard uses "Best power efficiency / Balanced / Best performance"; Classic uses "Recommended / Better performance / Best performance", matching what Windows Settings shows on that machine.
- Setting a mode: `00000000` and `ded574b5` go through the documented API as today. `3af9b8d9` is not a supported value for the documented API, so set it with `PowerSetActiveOverlayScheme` directly instead of relying on the documented call failing first. Verify on the Surface that Settings then shows "Better Performance".
- Reading: the reading logic already prefers the overlay when it is `3af9b8d9`. Map every GUID through the current set; a GUID that is not in the current set but is in the other set is a detection signal (8c), not an error.

**8c. Choosing the set**
- New setting `ModeSet`: `Auto` (default), `Standard` or `Classic`, saved with source-generated JSON.
- Auto detection, using modes chosen **outside the app** (ignore reads within a few seconds of the app's own set calls, so the app cannot fool itself):
  - Seeing `3af9b8d9` on either power source means Classic.
  - Seeing `961cc777` means Standard.
  - Seeing only `00000000` and `ded574b5` means undecided.
- Save the detected set so it survives restarts. A later outside sighting of the other set's GUID switches it and shows a short tray notification.
- While undecided, behave as Standard (today's behavior), and show a **one-time question** the first time the widget appears: "Which options does Windows show under Settings > Power mode?" with the two label lists as buttons, plus a button that opens `ms-settings:powersleep`. The answer is saved. Do not ask again unless the user picks Automatic from the menu.
- Right-click menu: **Power mode options** submenu with Automatic, Standard (Best power efficiency / Balanced / Best performance) and Classic (Recommended / Better performance / Best performance), radio-style.
- Use the two machines' Copy diagnostics output to check whether anything in the registry or the APIs tells the sets apart without a sighting (for example, which overlay subkeys exist). If a reliable signal turns up, use it for Auto and record it in `docs/power-mode-guids.md`. If not, keep the sighting rule and the question.

**8d. Edge cases**
- A GUID in neither set: neutral "unknown" state as today, plus a tray notification suggesting Copy diagnostics. Never guess.
- Active power plan not Balanced or derived from it: show "Power mode needs the Balanced power plan" in the status line and tooltip, because Windows ignores Power Mode on other plans. List plans at run time (`PowerEnumerate` + `PowerReadFriendlyName`); PC maker plan GUIDs differ per install.
- Energy Saver handling (section 3) stays as it is.
- The development laptop must behave exactly as it does today.

**Check:**
1. Development laptop: run the full section 9 checklist. Pick "Best power efficiency" in Windows Settings and confirm the set is Standard; the one-time question does not appear after that.
2. Surface Laptop, starting from a fresh `settings.json`: pick "Better Performance" in Windows Settings. The widget switches to Classic and shows the sailboat with Classic labels.
